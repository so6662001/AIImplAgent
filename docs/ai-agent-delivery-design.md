## 一、现状分析与痛点识别

### 1.1 现有交付流程全景

```
项目安排 → 客户调研 → 交付计划 → 深度调研 → 模拟演练 → 培训 → 期初数据 → 建帐导数 → 启用帐套 → 跟进辅助 → 成果交付 → 售后跟进
   ①         ②          ③         ④          ⑤        ⑥        ⑦          ⑧          ⑨         ⑩          ⑪          ⑫
```

### 1.2 各环节痛点分析

| 环节 | 当前方式 | 核心痛点 | 耗时占比(估) |
|------|---------|---------|-------------|
| ①项目安排 | 人工调度，凭经验分配PM | 分配不均，难以全局优化 | 2% |
| ②客户调研 | PM电话/现场沟通 | 调研模板不统一，信息遗漏 | 8% |
| ③交付计划 | PM手工制作文档 | 文档格式不一，耗时久 | 5% |
| ④深度调研 | 团队进场，手工整理分析 | 分析维度多、整理工作量大 | 15% |
| ⑤模拟演练 | 手动配置演示环境 | 环境准备慢，场景覆盖不全 | 10% |
| ⑥培训 | 人工培训，重复讲解 | 人力成本极高，效果参差 | 15% |
| ⑦期初数据 | 手工整理、核对 | 数据量大、错误率高 | 10% |
| ⑧建帐导数 | 手工操作 | 操作繁琐、易出错 | 8% |
| ⑨启用帐套 | 人工检查确认 | 检查项多、遗漏风险 | 3% |
| ⑩跟进辅助 | 驻场人员 | 人力成本最高 | 12% |
| ⑪成果交付 | 人工编写报告 | 数据汇总慢、文档工作量大 | 5% |
| ⑫售后跟进 | 人工接线/远程 | 重复问题多、响应慢 | 7% |

### 1.3 关键问题总结

1. **重复性工作占比高**：模板文档生成、数据整理校验、常见问题解答等大量重复劳动
2. **经验难以沉淀**：PM个人经验难以标准化传承
3. **信息孤岛**：各环节信息传递依赖人工，存在断层
4. **质量不稳定**：强依赖个人能力，交付质量波动大
5. **响应效率低**：培训与售后均需人工实时响应

## 二、AI介入可行性评估矩阵

### 2.1 评估维度说明

- **AI替代度**：该环节工作可被AI替代的程度（高/中/低）
- **技术成熟度**：当前AI技术实现该能力的成熟度（高/中/低）
- **业务价值**：AI介入后带来的降本增效价值（高/中/低）
- **实施难度**：技术实施与业务适配的难度（高/中/低）

### 2.2 评估矩阵

| 环节 | AI替代度 | 技术成熟度 | 业务价值 | 实施难度 | 优先级 | 建议策略 |
|------|---------|-----------|---------|---------|--------|---------|
| ①项目安排 | 中 | 高 | 中 | 低 | P2 | AI辅助推荐，人工决策 |
| ②客户调研 | 中 | 高 | 高 | 中 | P1 | AI生成调研框架+智能问卷 |
| ③交付计划 | 高 | 高 | 高 | 低 | P0 | AI自动生成，人工审核 |
| ④深度调研 | 中 | 中 | 高 | 中 | P1 | AI辅助分析+报告生成 |
| ⑤模拟演练 | 中 | 中 | 中 | 高 | P2 | AI生成演练场景+环境配置 |
| ⑥培训 | 高 | 高 | 高 | 中 | P0 | AI培训助手+智能问答 |
| ⑦期初数据 | 高 | 高 | 高 | 中 | P0 | AI数据清洗校验 |
| ⑧建帐导数 | 高 | 高 | 高 | 低 | P1 | AI自动化执行 |
| ⑨启用帐套 | 中 | 高 | 中 | 低 | P2 | AI检查清单自动化 |
| ⑩跟进辅助 | 高 | 高 | 高 | 中 | P0 | AI智能客服替代驻场 |
| ⑪成果交付 | 高 | 高 | 中 | 低 | P1 | AI自动生成报告 |
| ⑫售后跟进 | 高 | 高 | 高 | 低 | P0 | AI客服+工单智能流转 |

| ⑬智能录入辅助 | 高 | 高 | 高 | 中 | P0 | AI实时答疑+操作视频推送 |

### 2.3 优先级分组

- **P0（立即启动）**：③交付计划生成、⑥智能培训、⑦数据清洗、⑩智能跟进、⑫智能售后、**⑬智能录入辅助**
- **P1（次期推进）**：②调研辅助、④深度分析、⑧自动建帐、⑪报告生成
- **P2（远期规划）**：①智能调度、⑤演练生成、⑨上线检查

### 3.2 核心设计原则

1. **人机协同（Human-in-the-Loop）**：AI辅助不替代，关键决策必须有人工审核确认节点
2. **知识驱动**：以钢铁行业交付知识库为核心，持续积累沉淀
3. **可编排**：智能体独立运行，也可组合编排成复杂工作流
4. **渐进增强**：从辅助到半自动到自动，逐步提升AI参与度
5. **可观测**：所有AI决策过程可追溯、可审计

## 四、各智能体详细设计

### 4.1 项目调度智能体（Project Dispatch Agent）

**对应环节**：① 项目安排，确定项目经理

**核心能力**：
- 基于项目特征（客户规模、行业细分、系统复杂度）和PM画像（技能矩阵、当前负载、历史业绩、客户评价）进行智能匹配
- 输出推荐的PM人选及匹配理由

**输入**：
```
{
  "project_info": {
    "customer_name": "客户名称",
    "industry_segment": "钢贸/钢厂/加工中心/...",
    "estimated_scale": "大/中/小",
    "modules": ["进销存", "财务", "仓储", "MES", "智能财务", "智能采购", "智能录入", ...],
    "special_requirements": "特殊需求描述",
    "expected_start_date": "预计启动日期",
    "region": "所在地区"
  }
}
```

**输出**：
```
{
  "recommended_pms": [
    {
      "pm_id": "PM001",
      "name": "张三",
      "match_score": 92,
      "match_reasons": [
        "具有5个钢贸企业交付经验",
        "当前负载率60%，有余量",
        "距离客户所在地较近"
      ],
      "risk_notes": "近期有一个项目即将上线，需关注时间冲突"
    }
  ],
  "schedule_suggestion": {
    "recommended_start": "2026-05-01",
    "estimated_duration": "45天",
    "key_milestones": [...]
  }
}
```

**AI策略**：
- 使用规则引擎 + LLM混合模式
- 硬约束（资质、可用性）用规则过滤，软约束（匹配度）用LLM评分
- 持续学习：项目完成后的评价数据反馈到匹配模型

### 4.2 调研分析智能体（Research Agent）

**对应环节**：② 联系客户做项目调研 + ④ 深度调研

**核心能力**：
- 根据客户行业/规模/经营模式，自动生成定制化调研问卷和访谈提纲
- 实时辅助PM进行调研：语音转文字 → 关键信息提取 → 结构化沉淀
- 自动生成客户背景分析报告

**子能力拆分**：

#### 4.2.1 调研问卷生成器

**Prompt模板设计思路**：
```
角色：你是一位钢铁行业管理软件的资深实施顾问
任务：根据以下客户初步信息，生成一份结构化的调研问卷

客户信息：
- 企业类型：{enterprise_type} (钢贸商/钢厂/加工中心/综合服务商)
- 预估规模：{scale}
- 意向模块：{modules}

要求覆盖以下维度：
1. 经营模式分析（直营/代理/混合，内贸/外贸）
2. 经营品类（板材/型材/管材/特钢/不锈钢等，规格/材质/品牌分布）
3. 生产能力（仅生产型企业：产线数量/类型/产能/排班/MES现状/质量标准）
4. 库存与仓储（库存量级，仓库数量/面积(㎡)/行车数量与吨位，库存周转率）
5. 销售状况（月均销售量/金额，定价模式，结算方式，销售模式）
6. 客户群体（客户数量，客户类型分布，主要大客户）
7. 组织架构（部门设置，人员规模，关键岗位）
8. 现有IT系统（在用系统，痛点，数据情况）
9. 目标模块需求（进销存/财务/仓储/MES/智能财务/智能采购/智能录入）
10. 管理诉求与目标

请根据企业类型重点调整问卷侧重点：
- 生产型企业(钢厂/加工中心)重点覆盖 产线信息、MES需求、质量管理
- 现货批发企业(钢贸商)重点覆盖 仓库数量/面积/行车数、库存管理
- 所有企业均需采集 智能财务/智能采购/智能录入 的需求深度
```

#### 4.2.3 背景分析报告生成器

- 项目成果定义建议

### 4.3 计划生成智能体（Plan Generator Agent）

**对应环节**：③ 项目交付计划制作

**核心能力**：
- 基于客户画像、项目范围、历史同类项目数据，自动生成项目交付计划
- 包含：里程碑、任务分解（WBS）、资源需求、时间排期、风险预案

**输入**：
```
{
  "customer_profile": { ... },        // 来自调研分析智能体
  "project_scope": {
    "modules": ["进销存", "财务", "仓储", "MES", "智能财务", "智能采购", "智能录入"],
    "customization_level": "标准/轻度定制/深度定制",
    "integration_requirements": ["ERP对接", "银行接口"]
  },
  "constraints": {
    "deadline": "2026-08-01",
    "budget": "...",
    "available_resources": [...]
  }
}
```

**输出**：
```
{
  "project_plan": {
    "milestones": [
      { "name": "调研完成", "date": "...", "deliverables": [...] },
      { "name": "模拟演练通过", "date": "...", "deliverables": [...] },
      { "name": "培训完成", "date": "...", "deliverables": [...] },
      { "name": "正式上线", "date": "...", "deliverables": [...] },
      { "name": "交付验收", "date": "...", "deliverables": [...] }
    ],
    "wbs": [...],           // 详细任务分解
    "resource_plan": [...],  // 人员与资源计划
    "risk_plan": [...],      // 风险预案
    "gantt_data": [...]      // 甘特图数据
  }
}
```

**AI策略**：
- RAG检索历史同类项目计划作为参考
- LLM基于参考案例 + 当前项目约束生成新计划
- 内置钢铁行业交付最佳实践知识库
- 自动识别高风险节点并标注

### 4.4 模拟演练智能体（Simulation Agent）

**对应环节**：⑤ 模拟演练软件系统

**核心能力**：
- 根据客户业务场景自动生成模拟数据和测试用例
- 自动化场景配置：根据客户品类/流程特点配置演示环境
- 演练偏差检测：对比预期结果与实际演练结果

**核心功能**：

1. **模拟数据生成**
   - 根据客户经营品类，自动生成仿真的产品目录、客户档案、供应商档案
   - 根据库存量级和销售规模生成合理的模拟业务数据
   - 保证数据间的逻辑一致性（例如：库存数 = 入库数 - 出库数）

2. **演练场景脚本生成**
   - 基于客户业务流程，自动编排演练场景脚本
   - 覆盖核心业务路径 + 异常/边界场景
   - 输出step-by-step的操作指南

3. **演练结果评估**
   - 演练过程中自动记录操作日志
   - 与预期结果对比，标记偏差项
   - 生成《模拟演练评估报告》

**AI出题策略**：

```
考核题目生成规则:

1. 题型结构:
   ├─ 选择题 (40%) — 考察概念理解
   │   AI从培训内容中提取关键知识点，生成单选/多选题
   │
   ├─ 判断题 (15%) — 考察易混淆点
   │   AI基于常见错误和易混淆操作生成
   │
   ├─ 操作题 (30%) — 考察实际操作能力 ★核心
   │   AI给出业务场景，学员在系统中实际操作
   │   系统自动记录操作步骤 → AI判定是否正确
   │   例: "请完成一笔热轧卷板的采购入库操作"
   │
   └─ 场景题 (15%) — 考察综合应用
       AI模拟真实业务场景，考察流程串联能力
       例: "客户退货了一批不合格的镀锌板，请完成从退货到入库到索赔的全流程"

2. 难度分级:
   ├─ 基础级: 单一功能操作 (培训第1-3天考核)
   ├─ 进阶级: 多步骤流程串联 (培训第4-7天考核)
   └─ 综合级: 跨模块复杂场景 (培训结束前综合考核)

3. 出题智能化:
   - 同岗位不同人，题目相同但选项/数据随机打乱（防抄袭）
   - 重考时自动生成新题，重点覆盖上次的薄弱点
   - 根据学员学习进度动态调整题目难度
```

#### 4.6.2 导入依赖顺序与编排

期初数据之间存在严格的 **引用依赖关系**，必须按正确顺序导入。AI智能体自动识别并编排导入顺序：

```
导入阶段编排（严格依赖序）:

第1批 ─── 基础设置（无外部依赖）
 │  ├─ A1. 企业资料
 │  ├─ C1. 财务科目
 │  └─ A5. 账号资料（银行/现金账户）
 │
第2批 ─── 组织与人员（依赖企业资料）
 │  ├─ A2. 部门架构        ← 依赖：企业资料
 │  ├─ A3. 员工档案        ← 依赖：部门架构
 │  └─ A4. 用户档案        ← 依赖：员工档案
 │
第3批 ─── 业务档案（依赖基础设置）
 │  ├─ B1. 客户档案        ← 依赖：无（独立主数据）
 │  ├─ B2. 供应商档案      ← 依赖：无（独立主数据）
 │  ├─ B3. 货品类别        ← 依赖：无（独立主数据）
 │  ├─ B4. 货品方案        ← 依赖：货品类别
 │  ├─ B5. 仓库档案        ← 依赖：无（独立主数据）
 │  ├─ B6. 库位档案        ← 依赖：仓库档案
 │  └─ B7. 相关单位档案     ← 依赖：无（独立主数据）
 │
第4批 ─── 期初余额（依赖所有档案类数据）
 │  ├─ D1. 库存期初数      ← 依赖：货品方案、仓库、库位
 │  ├─ D2. 客户往来期初数   ← 依赖：客户档案（余额正负自动拆分应收/预收）
 │  ├─ D3. 供应商往来期初数  ← 依赖：供应商档案（余额正负自动拆分应付/预付）

 │  ├─ D5. 科目余额        ← 依赖：财务科目
 │  ├─ D6. 其他应收余额     ← 依赖：相关单位档案、财务科目

    ├─ E1. 应开销项发票期初数 ← 依赖：客户档案、货品方案
    └─ E2. 应收进项发票期初数 ← 依赖：供应商档案、货品方案
```

**AI编排策略**：
- 同一批次内的数据可并行导入
- 上一批次全部校验通过后才启动下一批次
- 任一数据项导入失败不阻塞同批次其他项，但阻塞下游依赖项
- 自动检测循环依赖并报警

```
B4核心处理分两部分：一是编码生成，二是数据标准化。

═══════════════════════════════════════════════════════════════
  第一部分：货品编码智能生成引擎
═══════════════════════════════════════════════════════════════

总体规则:
  - 导入数据中已有编码 → 保留原编码不变，仅做唯一性校验
  - 导入数据中无编码（为空）→ AI根据品类+规格自动生成

编码结构:
  货品编码 = 品类编码 + 规格编码串

  ┌──────────┬──────────────────────────────────────────────┐
  │ 品类编码  │ 规格编码串（由品类决定编码规则）                 │
  │ (来自B3) │ (AI根据规格参数按"由小到大/由薄到厚"排列生成)   │
  └──────────┴──────────────────────────────────────────────┘

═══ 各品类编码规则 ═══

┌──────────────────────────────────────────────────────────────────────┐
│ 1. 板材类（热轧/冷轧/镀锌/中厚板等）                                  │
│                                                                        │
│    规格结构: 厚度 × 宽度 × 长度(或C)                                  │
│    编码规则: 品类编码 + 厚度码 + 宽度码                                │
│    排序原则: 厚度由薄到厚，同厚度下宽度由窄到宽                         │
│                                                                        │
│    厚度码: 去小数点后补齐4位 (如 0.5mm→0050, 3.0mm→0300, 12mm→1200)  │
│    宽度码: 4位数字 (如 1000→1000, 1250→1250, 1500→1500)              │
│                                                                        │
│    示例 (品类编码=BC, 热轧卷板):                                       │
│    规格            │ 厚度码 │ 宽度码 │ 生成编码                         │
│    ────────────────┼────────┼────────┼────────────────────             │
│    0.5*1000*C      │ 0050   │ 1000   │ BC00501000                      │
│    0.5*1250*C      │ 0050   │ 1250   │ BC00501250                      │
│    1.5*1250*C      │ 0150   │ 1250   │ BC01501250                      │
│    3.0*1250*C      │ 0300   │ 1250   │ BC03001250                      │
│    3.0*1500*C      │ 0300   │ 1500   │ BC03001500                      │
│    12.0*2200*6000  │ 1200   │ 2200   │ BC12002200                      │
│                                                                        │
│    → 编码天然满足"由薄到厚、由窄到宽"的排序规则                         │
└──────────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────────┐
│ 2. 方矩管                                                            │
│                                                                        │
│    规格结构: 边长 × 边宽 × 壁厚                                       │
│    编码规则: 品类编码 + 边长码 + 边宽码 + 壁厚码                       │
│    排序原则: 边长由小到大 → 同边长边宽由小到大 → 同边长边宽壁厚由薄到厚  │
│                                                                        │
│    边长码: 3位数字 (如 20→020, 100→100, 200→200)                     │
│    边宽码: 3位数字 (如 20→020, 40→040, 100→100)                      │
│    壁厚码: 去小数点后补齐3位 (如 1.0→010, 2.5→025, 10→100)           │
│                                                                        │
│    示例 (品类编码=GFJ, 方矩管):                                        │
│    规格             │ 边长码│ 边宽码│ 壁厚码│ 生成编码                   │
│    ─────────────────┼───────┼───────┼───────┼────────────────           │
│    20*20*1.0        │ 020   │ 020   │ 010   │ GFJ020020010              │
│    20*20*2.0        │ 020   │ 020   │ 020   │ GFJ020020020              │
│    20*40*1.5        │ 020   │ 040   │ 015   │ GFJ020040015              │

│    100*100*4.0      │ 100   │ 100   │ 040   │ GFJ100100040              │

│                                                                        │
│    → 编码天然满足"由小到大、由薄到厚"的排序规则                         │
└──────────────────────────────────────────────────────────────────────┘

═══ 编码生成引擎工作流 ═══

导入货品数据
    │
    ├─ 有编码 → 保留原编码
    │   └─ 唯一性校验（与已有编码不冲突）
    │
    └─ 无编码 → AI自动生成
        │
        ├─ Step 1: 确定品类编码
        │   品名/类别 → 匹配B3货品类别 → 取得品类编码
        │
        ├─ Step 2: 解析规格参数
        │   规格字符串 → 规格标准化引擎 → 提取数值参数
        │   例: "20*40*1.5" → { 边长:20, 边宽:40, 壁厚:1.5 }
        │
        ├─ Step 3: 判断品类编码规则
        │   ├─ 板材类 → 厚度码+宽度码
        │   ├─ 方矩管 → 边长码+边宽码+壁厚码
        │   ├─ 圆管类 → 外径码+壁厚码
        │   ├─ 型材类 → 按型材子类规则
        │   ├─ 线材/建材 → 直径码
        │   └─ 非钢材 → 顺序号
        │
        ├─ Step 4: 拼接编码
        │   货品编码 = 品类编码 + 规格编码串
        │
        ├─ Step 5: 唯一性校验
        │   如与已有编码冲突（同编码不同货品）→ 末尾追加区分后缀
        │   例: BC03001250 已存在 → BC03001250A
        │
        └─ Step 6: 排序校验
            全部编码生成后，AI验证同品类内编码的排序是否满足
            "由小到大、由薄到厚"的规则，不满足则告警

═══ 编码生成的前置条件 ═══

货品编码生成依赖B3货品类别的品类编码已经建立。
AI在生成编码前会检查:
  1. 该货品的品类是否已在B3中注册 → 未注册则无法生成
  2. 该品类编码是否已配置编码规则 → 未配置则使用默认规则(品类码+顺序号)
  3. 规格是否已标准化 → 未标准化的规格无法提取参数，退回到规格标准化步骤
```

```
═══════════════════════════════════════════════════════════════
  第二部分：数据标准化引擎
═══════════════════════════════════════════════════════════════

1. 品名标准化（同义词库）:
   ┌──────────────────┬───────────────────────────┐
   │ 标准品名          │ 同义词/别名                 │
   ├──────────────────┼───────────────────────────┤
   │ 热轧卷板          │ 热轧卷、热卷、HRC、热板      │
   │ 冷轧卷板          │ 冷轧卷、冷卷、CRC、冷板、SPCC│
   │ 镀锌板            │ 镀锌卷、白铁皮、GI            │
   │ 热轧酸洗板        │ 酸洗板、酸洗卷、PL            │
   │ 螺纹钢            │ 螺纹、HRB400、抗震钢筋、螺纹钢筋│
   │ H型钢             │ H钢、H形钢、H型              │
   │ 无缝钢管          │ 无缝管、无缝                  │
   │ 方矩管            │ 方管、矩管、方钢管、矩形管      │
   └──────────────────┴───────────────────────────┘

2. 规格标准化引擎:
   输入各种格式 → 解析 → 输出标准格式 + 提取数值参数(供编码生成使用)

   板材/卷板: 厚度*宽度*长度(或C)
     "3.0*1250*C"    → { 厚:3.0, 宽:1250, 长:"C(卷)" }  ✓ 标准
     "3.0×1250×C"    → 转换为 "3.0*1250*C"
     "3*1250*卷"     → 转换为 "3.0*1250*C"
     "3.0mm*1250mm*C"→ 转换为 "3.0*1250*C"

   方矩管: 边长*边宽*壁厚
     "20*40*1.5"     → { 边长:20, 边宽:40, 壁厚:1.5 }
     "20×40×1.5"     → 转换为 "20*40*1.5"
     "□20*40*1.5"    → 转换为 "20*40*1.5"

   型材: 规格型号
     "H200*200*8*12" → { H:200, B:200, tw:8, tf:12 }
     "HW200×200"     → 补全为 "H200*200*8*12"(查标准表)

   圆管: 外径*壁厚*长度
     "Φ219*8*12000"  → { OD:219, WT:8, L:12000 }
     "219×8×12m"     → 转换为 "Φ219*8*12000"

   线材/建材: 直径
     "Φ8"/"φ8"/"8mm" → { 直径:8 }
   
3. 材质标准化引擎:
   "Q235"    → "Q235B"  (默认补全子级)
   "q235b"   → "Q235B"  (大写标准化)
   "Q345"    → "Q345B"  (默认补全子级)
   "SS400"   → "Q235B"  (日标转国标映射)
   "SPHC"    → 保留      (日标热轧通用，标记为进口)
   "DC01"    → 保留      (欧标，标记为进口)
   
   AI额外校验: 品名与材质是否匹配
   例: "螺纹钢" + "SPCC" → 告警（SPCC通常用于冷轧，不用于螺纹钢）

4. 钢厂名称标准化:
   使用B2中的钢厂名称库进行统一

5. 件重合理性校验(基于理论计算):
   板材理论重量 = 厚(mm) × 宽(mm) × 长(mm) × 密度(7.85g/cm³)
   偏差超过±5%标记为异常，提醒人工确认
```

**字段清单（用户录入字段 + AI计算字段）**：

```
┌──────────────────────────────────────────────────────────────────────────┐
│                     库存期初数字段体系                                     │
│                                                                          │
│  ═══ 基础引用字段（用户填写或选择） ═══                                   │
│  ├─ 货品编码 (引用B4)                                                    │
│  ├─ 品名、规格、材质、钢厂     ← 选择货品后自动带出                       │

│  ├─ 数量           ← 用户录入（件/张/卷/根/捆等，取决于货品计量单位）      │
│  ├─ 重量(吨)       ← 用户录入（如帐套不使用重量，则系统自动令 重量=数量）  │
│  ├─ 包装数量       ← 用户录入（每包/每捆/每件的标准数量）                 │

│                                                                          │
│  ═══ AI自动计算字段 ═══                                                  │
│  ├─ 整件数         ← = 数量 ÷ 包装数量 的整数部分（向下取整）             │

│  ├─ 成本金额(元)   ← = 重量(吨) × 成本单价(元/吨)                       │
│  └─ 单位重量(kg)   ← = 重量(吨) × 1000 ÷ 数量                          │
│                                                                          │
│  ═══ 精度控制 ═══                                                        │
│  所有AI计算结果按ERP帐套中配置的精度保留小数位:                            │
│  ├─ 整件数: 整数（无小数）                                               │
│  ├─ 零数: 取帐套"数量精度"设置（如: 0位/2位/4位小数）                    │
│  ├─ 成本金额: 取帐套"金额精度"设置（通常2位小数）                        │
│  └─ 单位重量: 取帐套"重量精度"设置（如: 2位/3位/4位小数）                │
└──────────────────────────────────────────────────────────────────────────┘
```

**AI校验规则**：货品编码存在性；仓库/库位引用有效性；成本金额=重量×成本单价(按帐套金额精度校验)；整件数+零数反算=数量；单价合理性(对比市场价±30%)；汇总成本金额=科目余额"库存商品"科目(D5)

```
AI自动计算引擎 — 详细规则:

═══ 1. 整件数与零数计算 ═══

公式:
  整件数 = FLOOR(数量 ÷ 包装数量)    // 向下取整
  零数   = 数量 - 整件数 × 包装数量   // 按帐套数量精度四舍五入

示例(包装数量=10):
  ┌──────────┬──────────┬──────────┬──────────┐
  │ 数量      │ 包装数量  │ 整件数    │ 零数      │
  ├──────────┼──────────┼──────────┼──────────┤
  │ 53       │ 10       │ 5        │ 3        │
  │ 100      │ 10       │ 10       │ 0        │
  │ 7        │ 10       │ 0        │ 7        │
  │ 25.5     │ 10       │ 2        │ 5.5      │  ← 零数保留帐套精度
  └──────────┴──────────┴──────────┴──────────┘

特殊情况处理:
  - 包装数量为空或0 → 整件数=0, 零数=数量（全部为散件）
  - 数量为0 → 整件数=0, 零数=0（空库存记录，标记告警）

反算校验:
  整件数 × 包装数量 + 零数 必须 = 数量（精度内一致）
  不一致 → 标红，提示计算异常


═══ 2. 成本金额计算 ═══

公式:
  成本金额 = 重量(吨) × 成本单价(元/吨)
  → 按帐套"金额精度"四舍五入

示例(帐套金额精度=2位小数):
  ┌──────────┬───────────┬──────────────────┐
  │ 重量(吨)  │ 成本单价   │ 成本金额          │
  ├──────────┼───────────┼──────────────────┤
  │ 25.380   │ 3,850.00  │ 97,713.00        │  ← 25.380×3850=97713.00
  │ 3.265    │ 4,200.50  │ 13,714.63        │  ← 3.265×4200.5=13714.6325→13714.63
  │ 0.850    │ 5,100.00  │ 4,335.00         │
  └──────────┴───────────┴──────────────────┘

帐套不使用重量的情况:
  当帐套设置"不使用重量"时:
  → 系统自动令 重量 = 数量
  → 成本单价单位变为 元/计量单位（而非元/吨）
  → 成本金额 = 数量 × 成本单价

  示例(不使用重量，计量单位=件):
  ┌──────────┬───────────┬──────────────────┐
  │ 数量(件)  │ 成本单价   │ 成本金额          │
  ├──────────┼───────────┼──────────────────┤
  │ 100      │ 350.00    │ 35,000.00        │
  │ 53       │ 420.50    │ 22,286.50        │
  └──────────┴───────────┴──────────────────┘


═══ 3. 单位重量计算 ═══

公式:
  单位重量(kg) = 重量(吨) × 1000 ÷ 数量
  → 按帐套"重量精度"四舍五入

示例(帐套重量精度=3位小数):
  ┌──────────┬──────────┬──────────────────┐
  │ 重量(吨)  │ 数量      │ 单位重量(kg)      │
  ├──────────┼──────────┼──────────────────┤
  │ 25.380   │ 10       │ 2,538.000        │  ← 每件2.538吨
  │ 3.265    │ 5        │ 653.000          │
  │ 0.850    │ 1        │ 850.000          │
  │ 12.750   │ 3        │ 4,250.000        │
  └──────────┴──────────┴──────────────────┘

帐套不使用重量的情况:
  → 单位重量不计算，该字段隐藏或显示为"—"

特殊情况:
  - 数量=0 → 单位重量无法计算，标记告警
  - 计算结果与该规格的理论件重偏差>±10% → 标黄提醒人工确认


═══ 4. ERP帐套精度配置读取 ═══

AI计算前自动读取帐套精度配置:

┌──────────────┬──────────────┬──────────────────────────┐
│ 精度参数      │ 帐套配置项    │ 常见设置                  │
├──────────────┼──────────────┼──────────────────────────┤
│ 数量精度      │ qty_decimals │ 0位(整件) / 2位 / 4位     │
│ 重量精度      │ wgt_decimals │ 2位 / 3位 / 4位           │
│ 单价精度      │ prc_decimals │ 2位 / 4位                 │
│ 金额精度      │ amt_decimals │ 2位(最常见)               │
│ 是否使用重量   │ use_weight   │ true / false             │
└──────────────┴──────────────┴──────────────────────────┘

精度规则:
  - 所有AI计算结果统一使用四舍五入(HALF_UP)
  - 帐套精度在建帐套阶段由帐套管理Agent(4.6.6)根据客户画像自动推荐
  - 精度一旦启用后不可修改（财务规范要求）
  - 导入数据中如果已有计算值，AI用公式重新计算并与原值比对，偏差超过精度则标记


═══ 5. 高级校验 ═══

1. 单价合理性检查:
   - 对比近期市场价格（可接入钢铁价格指数API）
   - 热轧卷板 Q235B 3.0*1250*C 当前市价约 3,800元/吨
   - 如果期初单价为 38,000元/吨 → 标红：可能是单位错误（元 vs 元/吨）
   - 如果期初单价为 380元/吨 → 标红：价格异常偏低

2. 单位重量(件重)合理性:
   - AI计算出的单位重量 vs 该规格的理论件重
   - 板材理论件重 = 厚(mm) × 宽(mm) × 长(mm) × 7.85 ÷ 10⁹ (吨)
   - 偏差>±10% → 标黄提醒人工确认
   - 偏差>±30% → 标红可能数据错误

3. 整件数/零数反算一致性:
   - 整件数 × 包装数量 + 零数 = 数量（精度内）
   - 不一致 → 标红

4. 帐套不使用重量时的额外校验:
   - 确认 重量=数量（系统自动赋值）
   - 确认 成本单价单位正确（元/件 而非 元/吨）

5. 库存汇总 → 科目余额对账:
   Σ成本金额 必须等于 科目余额中"库存商品"科目的期初余额
   不平时自动列示差异明细

6. 精度尾差累计检查:
   由于四舍五入，大量明细行的尾差可能累计
   AI自动检测: |Σ明细成本金额 - 科目余额| 如果差异≤明细行数×0.01
   → 属于精度尾差，自动标注说明，建议在最后一行做尾差调整
```

**导入执行策略**：

```
多服务器导入执行流程:

Step 1: 连接预检
  ├─ 检测目标服务器网络连通性（Ping + 端口探测）
  ├─ 验证数据库连接凭证有效性
  ├─ 确认ERP系统版本与导入接口兼容性
  ├─ 检查目标数据库字符集（避免乱码）
  └─ 不通过 → 告警，暂停导入，通知工程师排查

Step 2: 环境适配
  ├─ 读取目标帐套的精度配置（数量/重量/金额小数位）
  ├─ 读取目标帐套的编码规则（确保导入编码符合规则）
  ├─ 检查目标数据库表结构版本（不同ERP版本表结构可能不同）
  └─ 自动适配SQL/API调用方式

Step 3: 导入方式选择
  ├─ 方式A: API导入（优先推荐）
  │   通过ERP系统提供的标准API接口导入
  │   优点: 经过业务逻辑校验，安全性高
  │   适用: ERP系统提供了完善的导入API
  │
  ├─ 方式B: 数据库直写（需审慎使用）
  │   直接写入数据库表
  │   优点: 速度快，适合大数据量
  │   风险: 绕过业务逻辑，需AI额外校验完整性
  │   适用: 大数据量期初导入 + 工程师确认
  │
  └─ 方式C: 导入文件推送
      生成目标系统格式的导入文件，推送到服务器
      由ERP系统内置的导入功能执行
      适用: 无法直连数据库的安全隔离环境

Step 4: 分批导入 + 事务控制
  ├─ 按4.6.2节定义的5个批次顺序执行
  ├─ 每批次在独立事务中执行
  ├─ 单批次失败 → 自动回滚当前批次
  ├─ 支持断点续传（记录已完成的批次，异常恢复后从断点继续）
  └─ 导入进度实时推送到工程师工作台

Step 5: 导入后验证
  ├─ 在目标服务器上执行数据完整性校验
  ├─ 对比导入前后的记录数
  ├─ 执行关键勾稽关系检查（直接在目标库上验证）
  └─ 生成《导入验证报告》
```

**安全保障**：

```
多服务器环境下的安全措施:

1. 凭证安全
   ├─ 数据库密码/API Token使用AES-256加密存储
   ├─ 凭证仅在导入执行瞬间解密，用后立即清除内存
   ├─ 凭证变更后自动失效旧凭证
   └─ 支持通过密钥管理服务(KMS)管理

2. 传输安全
   ├─ 所有数据传输必须经过SSL/TLS加密通道
   ├─ 不支持明文传输
   └─ 支持VPN通道连接客户内网服务器

3. 权限隔离
   ├─ 每个项目只能访问对应客户的服务器
   ├─ 导入账号使用最小权限原则（仅INSERT/UPDATE，无DELETE/DROP）
   ├─ 导入完成后自动锁定导入账号
   └─ 所有导入操作写入审计日志

4. 数据隔离
   ├─ 清洗/校验在AI中台执行时，不同客户数据严格隔离
   ├─ 临时数据处理完成后自动清理
   └─ 不保留客户业务数据的明文副本（仅保留脱敏的统计摘要）
```

#### 4.11.5 视频知识库建设方案

```
视频生产流程:

┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐
│ 录屏采集  │───▶│ AI切片   │───▶│ 字幕生成 │───▶│ 索引入库  │
│          │    │ & 标注   │    │ & 翻译   │    │          │
└─────────┘    └─────────┘    └─────────┘    └─────────┘

1. 录屏采集:
   - 由实施团队在标准环境中录制各功能操作视频
   - 每个视频覆盖一个完整操作场景（3-5分钟）
   - 录制时使用标准化的操作步骤和解说脚本（由AI生成）

2. AI切片 & 标注:
   - AI自动识别视频中的操作步骤边界（基于画面变化检测）
   - 为每个切片打标签: 模块/功能/操作步骤/涉及字段
   - 生成切片时间戳索引

3. 字幕生成:
   - ASR自动生成字幕
   - AI校对字幕准确性（特别是钢铁行业术语）

4. 索引入库:
   - 视频元数据 + 切片索引 + 字幕文本 → 向量化入库
   - 建立 页面/字段 → 视频切片 的精确映射关系
   - 支持按关键词/语义 检索视频内容

视频更新策略:
   - 系统版本更新时，自动标记受影响的视频
   - 优先更新高频使用的视频
   - 支持增量录制（只录变更部分）
```

**与培训助手Agent(4.5)的协同**：
- 培训阶段：培训助手Agent使用完整视频进行系统培训
- 日常使用：智能录入Agent使用视频切片进行精准答疑
- 共享同一个视频知识库，避免重复建设
- 培训考核中的薄弱环节 → 自动关联到智能录入Agent的重点提示规则

### 4.12 交付人力管理智能体（Workforce Management Agent）

**对应环节**：贯穿全流程（组织管理层面，服务于交付部门总监和管理层）

**核心定位**：建立交付团队的 **人力评价体系** 和 **人力管理体系**，让每一位交付工程师的状态、能力、业绩、成长轨迹都有数据支撑，为人员调配、绩效考核、人才培养提供核心决策依据。

**核心能力**：
- **人力全景看板**：所有交付工程师的实时状态、位置、负载一目了然
- **项目评价体系**：从多维度对每个项目的交付质量进行评价
- **个人综合评价**：AI自动计算每人的综合评分，基于项目数据而非主观印象
- **人力效率分析**：空闲率、利用率、产能分析
- **未来排期预测**：自动推算未来两个月的人力安排和缺口
- **人员培养建议**：基于能力短板和成长趋势，AI给出培养方向建议

#### 4.12.4 AI综合评价算法

```
个人综合评分计算公式:

Score = Σ (维度得分 × 权重)

┌──────────────────────────────────────────────────────────────────┐
│                    综合评价六维模型                                │
│                                                                    │
│                      项目交付质量                                  │
│                       (35%) ★                                     │
│                      ╱      ╲                                     │
│             成长与贡献         客户满意度                           │
│              (10%)               (20%)                             │
│              │                      │                              │
│             团队协作           工作效率                             │
│              (10%)              (15%)                               │
│                      ╲      ╱                                     │
│                      过程规范                                      │
│                       (10%)                                        │
│                                                                    │
│  项目交付质量权重最高(35%)，体现"交付是核心业务"的价值导向          │
└──────────────────────────────────────────────────────────────────┘

各维度计算规则:

1. 项目交付质量 (35%)
   = 近6个月所有负责项目的PQI(项目质量指数)加权均值
   加权方式: 近3个月的项目权重×1.5，更早的项目权重×1.0
   如果近6个月无项目: 取历史最近的3个项目PQI

2. 客户满意度 (20%)
   = 近6个月客户评分均值 × 20 (5分制转100分制)
   + 投诉修正: 每次投诉 -5分
   + 推荐加分: 客户主动推荐 +2分/次

3. 工作效率 (15%)
   利用率得分: 利用率80%=85分为基准
     每高1% → +0.5分 (上限100分)
     每低1% → -1分 (下限60分)
   效率得分: 项目平均超期率 vs 部门平均
     优于平均 → 加分; 劣于平均 → 扣分
   最终得分 = 利用率得分×0.6 + 效率得分×0.4

4. 过程规范 (10%)
   = (日报提交率 + 文档归档率 + 流程合规率) / 3 × 100

5. 团队协作 (10%)
   = 项目团队互评均分 × 20 + 跨项目贡献加分
   团队互评: 项目结束后团队成员匿名打分(5分制)
   跨项目贡献: 帮助其他项目解决问题 +2分/次

6. 成长与贡献 (10%)
   知识库贡献: 每篇优质文档 +5分 (上限30分)
   新人带教: 每带教1人 +10分 (上限20分)
   内部培训: 每次讲师 +10分 (上限20分)
   获取认证: 每个认证 +10分 (上限20分)
   基础分30分 + 以上加分(上限100分)

评级标准:
  90-100分: ★★★★★ 卓越  →  晋升优先考虑
  80-89分:  ★★★★☆ 优良  →  绩效A/B
  70-79分:  ★★★☆☆ 合格  →  绩效B/C
  60-69分:  ★★☆☆☆ 待改进 → 需制定改进计划
  <60分:    ★☆☆☆☆ 不合格 → 需重点关注/谈话
```

### 6.4 AI智能体运行时核心设计

```java
// 智能体基础接口设计思路
public interface Agent {
    String getId();
    String getName();
    AgentType getType();
    AgentCapability[] getCapabilities();
    
    // 执行入口
    AgentResult execute(AgentContext context, AgentRequest request);
    
    // 流式执行（用于对话场景）
    Flux<AgentEvent> executeStream(AgentContext context, AgentRequest request);
}

// 智能体上下文
public class AgentContext {
    private String projectId;
    private String userId;
    private ProjectContext projectContext;  // 项目全局上下文
    private ConversationHistory history;    // 对话历史
    private Map<String, Object> variables;  // 运行时变量
}

// 智能体编排引擎
public interface AgentOrchestrator {
    // 执行编排好的工作流
    WorkflowResult executeWorkflow(String workflowId, ProjectContext context);
    
    // 根据用户意图自动选择并调用合适的智能体
    AgentResult dispatch(String userIntent, AgentContext context);
}
```

## 八、实施路径建议

### 8.1 分阶段实施计划

#### 第一阶段：基础设施 + P0智能体

**目标**：搭建AI智能体基础平台，上线最高价值的5个智能体

**范围**：
1. AI智能体基础平台搭建
   - LLM网关服务（支持多模型切换）
   - RAG检索服务 + 向量数据库
   - 知识库管理后台
   - Agent运行时引擎
   - AI对话前端组件

2. P0智能体开发
   - **计划生成Agent**（③）— 入手难度最低，见效快
   - **培训助手Agent**（⑥）— 降本效果明显
   - **数据治理Agent**（⑦）— 技术成熟，价值高
   - **现场辅助Agent**（⑩）— 降低驻场成本
   - **售后服务Agent**（⑫）— 独立性强，易落地
   - **智能录入Agent**（⑬）— 嵌入产品，降低用户学习成本，减少培训和售后压力

**技术关键项**：
- LLM网关搭建：GLM(客服/问答) + 通义千问(文档/分析) + Claude(推理/编排) 三模型路由
- 钢铁行业知识库构建（术语、品类、业务流程）
- **操作视频知识库建设**（录屏→AI切片→字幕→向量化索引）
- 历史项目数据整理与向量化
- 产品操作文档结构化

#### 第二阶段：P1智能体 + 流程串联

**目标**：补齐核心智能体，实现全流程AI协同

**范围**：
1. P1智能体开发
   - **调研分析Agent**（②④）
   - **帐套管理Agent**（⑧）
   - **交付报告Agent**（⑪）
   - **人力管理Agent**（⑭）— 建立人力评价体系，为管理层提供核心决策数据

2. 智能体编排引擎
   - 实现智能体间的上下文传递
   - 实现全流程自动编排
   - 人工审核节点集成

3. 知识库持续丰富
   - 项目经验自动沉淀
   - 问题解决方案自动归档

#### 第三阶段：P2智能体 + 智能化升级

**目标**：全面智能化，持续优化

**范围**：
1. P2智能体开发
   - **项目调度Agent**（①）
   - **演练配置Agent**（⑤）
   - **上线检查Agent**（⑨）

2. MES与智能模块深度集成
   - MES产线数据与交付系统打通
   - 智能财务 → AI自动生成凭证、异常检测、报表解读
   - 智能采购 → AI供应商推荐、价格预测、自动询价
   - 智能录入能力持续优化（基于用户行为数据迭代）

3. 智能化升级
   - 多模态能力（语音输入、图片识别）
   - 预测性分析（项目风险预测、客户流失预测）
   - 智能体自我学习与优化

## 九、风险与应对策略

### 9.1 技术风险

| 风险 | 影响 | 应对策略 |
|------|------|---------|
| LLM输出不准确/幻觉 | 生成错误方案影响交付 | 关键环节设人工审核；使用RAG约束回答范围；置信度评分低于阈值自动标记 |
| 数据安全泄露 | 客户敏感数据外泄 | 数据脱敏处理；使用私有化部署LLM（如本地部署开源模型）；数据按项目隔离 |
| LLM API不稳定 | 服务中断 | 多模型备份（主备切换）；关键功能降级方案（退回人工模式）|
| 向量检索精度不够 | AI回答质量差 | 多路召回+重排序；持续优化分块策略；人工标注优化 |

### 9.2 业务风险

| 风险 | 影响 | 应对策略 |
|------|------|---------|
| 用户排斥AI | 推广困难 | 先从内部PM试用，再推广到客户；AI作为辅助工具而非替代 |
| 知识库冷启动 | 初期AI表现差 | 组织老PM进行知识贡献；历史项目资料批量导入 |
| 过度依赖AI | 团队能力退化 | 保持关键环节人工参与；定期进行无AI演练 |
| 行业特殊性 | 通用AI不适用 | 持续投入行业知识库建设；行业专家参与Prompt调优 |

#### 9.3.2 各智能体模型分配总览

| 智能体 | 主模型 | 备用模型 | 选型理由 |
|--------|--------|---------|---------|
| 项目调度Agent | 通义千问 | Claude | 需要综合评估能力，千问中文理解强 |
| 调研分析Agent | 通义千问 | Claude | 文档生成+信息结构化，千问擅长 |
| 计划生成Agent | 通义千问 + Claude | — | 千问生成文档，Claude做复杂推理 |
| 模拟演练Agent | Claude | 通义千问 | 场景编排需要深度推理+代码生成 |
| 培训助手Agent | GLM(问答) + 千问(生成) | — | 实时问答用GLM低延迟；材料生成用千问 |
| 数据治理Agent | 通义千问(清洗) + Claude(校验) | — | 标准化用千问；跨表勾稽推理用Claude |
| 上线检查Agent | Claude | 通义千问 | 检查规则推理需要严谨逻辑 |
| 现场辅助Agent | **GLM** | 通义千问 | 实时问答，需要低延迟+高并发 |
| 交付报告Agent | 通义千问 | — | 中文报告生成，千问表现优异 |
| 售后服务Agent | **GLM** | 通义千问 | 7×24客服，需要低成本+低延迟 |
| **智能录入Agent** | **GLM**(答疑) + 千问(视频匹配) | — | 实时交互用GLM；内容理解用千问 |
| **人力管理Agent** | 通义千问(报表) + Claude(评价推理) | — | 报表生成用千问；综合评价推理用Claude |

#### 9.3.3 LLM网关路由策略

```
LLM网关路由设计:

请求进入 → 场景标识解析 → 模型路由
                              │
                ┌──────────────┼──────────────┐
                ▼              ▼              ▼
            GLM集群        千问集群        Claude API
          (私有化部署)    (API/私有化)      (API调用)
                │              │              │
                └──────────────┼──────────────┘
                               ▼
                          统一响应格式

路由规则:
1. 场景优先: 根据请求的agent_id和task_type确定主模型
2. 降级策略: 主模型超时/异常时自动切换到备用模型
3. 成本控制: 简单任务强制路由到GLM，避免使用高成本模型
4. 负载均衡: GLM和千问私有化实例间做负载均衡
5. 限流保护: Claude API设置请求频率限制和月度预算上限
```

#### 9.3.4 成本优化策略

| 策略 | 说明 |
|------|------|
| GLM私有化部署 | 客服/问答等高频场景使用私有化GLM，消除API调用成本 |
| 千问分级部署 | 简单任务用Qwen-7B/14B本地部署，复杂任务才调用Qwen-Max API |
| Claude按需调用 | 仅在需要深度推理的场景调用Claude API，严格控制Token用量 |
| 结果缓存 | 相同/相似查询结果缓存复用（如FAQ回答、标准化规则） |
| Prompt优化 | 持续优化Prompt减少Token消耗，使用Few-shot而非长指令 |
